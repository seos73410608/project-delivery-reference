# Architecture Rationale
## Evidence Context Intelligence

- **Feature**: Evidence Context Intelligence
- **Status**: Proposed
- **Version**: 1.0
- **Last Updated**: 2026-11-09

---

## 1. 문서 목적

본 문서는 Evidence Context Intelligence Feature의 아키텍처 설계 원칙과 기술 선택의 근거를 정의한다.

이번 Feature의 목표는 기존 PMIS의 Evidence 관리 기능을 단순히 확장하는 것이 아니다.

프로젝트 수행 과정에서 발생하는 업무 행위와 판단, 의사결정, 증적, 결과를 연결하여 개인에게 축적된 경험을 조직이 재사용할 수 있는 지식으로 발전시키는 기반을 마련하는 것이다.

이를 위해 다음 다섯 가지 아키텍처 원칙을 정의한다.

1. MariaDB를 업무 데이터의 System of Record로 유지한다.
2. Neo4j를 업무 관계 및 경험 탐색을 위한 저장소로 활용한다.
3. Spring AI를 자연어 기반 검색과 분석을 위한 프레임워크로 활용한다.
4. AI 생성 결과를 자동으로 공식 Knowledge로 확정하지 않는다.
5. 검토 및 승인된 Knowledge만 조직의 재사용 가능한 경험으로 인정한다.

본 문서는 기술 선택의 이유뿐 아니라 대안 기술과 비교한 판단 근거, 설계상 한계 및 향후 검증 항목을 함께 기록한다.

## 2. 해결하려는 문제

### 2.1 기존 프로젝트 관리 시스템의 한계

일반적인 프로젝트 관리 시스템은 프로젝트 수행에 필요한 업무 데이터를 관리하는 데 초점을 둔다.

대표적으로 다음과 같은 정보가 관리된다.

- 프로젝트 및 일정
- 작업 및 담당자
- 이슈 및 위험
- 변경 및 의사결정
- 산출물 및 증적
- 검수 및 승인 이력

그러나 이러한 정보가 개별 업무 단위로 축적되는 것만으로는 조직의 경험이 충분히 재사용되기 어렵다.

예를 들어 다음과 같은 상황을 생각할 수 있다.

- 이전 프로젝트에서 특정 서버 구성 문제가 발생했다.
- 담당자가 원인을 조사하고 해결 방법을 결정했다.
- 변경 작업을 수행하고 테스트 결과를 증적으로 남겼다.
- 프로젝트는 정상적으로 종료되었다.

이 과정의 기록이 시스템에 남아 있더라도 다른 프로젝트의 담당자가 동일하거나 유사한 문제를 해결할 때 관련 기록을 찾아내고, 당시 상황과 판단 근거를 이해하고, 현재 상황에 적용할 수 있는지 판단해야 한다.

즉, 단순한 데이터 보관과 조직 경험의 재사용 사이에는 차이가 존재한다.

### 2.2 해결 방향

본 Feature에서는 업무 수행 과정에서 발생하는 사실과 행위를 Business Event로 기록하고, 관련 이벤트와 원본 자료, 판단 근거 및 결과를 Context로 연결한다.

Context 중 검토 및 승인된 경험은 Knowledge로 관리한다.

전체 흐름은 다음과 같다.

`Work → Business Event → Context → Knowledge → Reuse`

각 단계의 책임은 다음과 같다.

| 단계 | 역할 |
|---|---|
| Work | 실제 업무 수행 |
| Business Event | 업무 과정에서 발생한 주요 행위와 사실 기록 |
| Context | 관련 이벤트, 원본 자료, 판단 및 결과의 연결 |
| Knowledge | 검토 및 승인된 재사용 가능 경험 |
| Reuse | 다른 프로젝트 및 업무에서 경험 활용 |

AI는 이 과정에서 관련 경험을 검색하고 분석하며 Context 및 Knowledge 후보를 생성하는 역할을 지원한다.

단, AI가 생성한 결과 자체를 검증된 조직 지식으로 간주하지 않는다.

## 3. 아키텍처 설계 원칙

### 3.1 MariaDB: System of Record

**설계 방향**

**설계 원칙**

MariaDB를 PMIS 업무 데이터의 원본 저장소(System of Record)로 유지한다.

#### 선택 근거

PMIS는 프로젝트, Evidence, Issue, Decision, Action 등 명확한 업무 규칙을 갖는 데이터를 관리한다.

이러한 데이터에는 다음과 같은 특성이 있다.

- 생성, 수정, 삭제 및 복원에 대한 업무 규칙이 존재한다.
- 사용자 및 역할에 따른 접근 권한이 필요하다.
- 업무 상태에 따른 전이 규칙이 존재한다.
- 여러 데이터 간 참조 무결성이 필요하다.
- 승인 및 변경 과정에서 트랜잭션 일관성이 중요하다.

특히 Evidence Version은 검증 상태, 삭제 정책, 복원 정책 및 원본 파일 참조를 관리해야 한다.

따라서 업무 데이터의 최종적인 신뢰성과 변경 책임은 기존 RDB 기반 도메인 서비스가 유지하는 것이 적절하다.

#### 적용 방향

- 프로젝트 및 업무 데이터는 MariaDB에서 관리한다.
- 업무 데이터 변경은 Spring Boot 도메인 서비스를 통해 수행한다.
- Evidence Version의 삭제 및 복원은 기존 업무 규칙을 유지한다.
- Business Event는 주요 업무 행위의 발생 사실을 기록한다.
- Neo4j에는 관계 탐색에 필요한 식별자와 최소한의 속성을 저장한다.
- 그래프 데이터는 MariaDB의 원본 업무 데이터를 기준으로 재생성할 수 있도록 설계한다.

#### 대안 비교

| 대안 | 장점 | 판단 |
|---|---|---|
| MariaDB 유지 | 트랜잭션, 참조 무결성, 기존 PMIS 활용 | 채택 |
| Neo4j를 원본 저장소로 사용 | 관계 탐색에 유리 | 업무 원본 관리에는 부적합 |
| RDB와 Graph DB에 업무 원본 중복 저장 | 조회 선택지 확대 | 데이터 정합성 및 변경 책임 복잡화 |

#### 설계 결과

MariaDB가 업무 데이터의 최종적인 기준이 된다.

Neo4j 또는 AI 검색 결과와 MariaDB 원본이 서로 다른 경우 MariaDB의 업무 데이터와 권한 정책을 기준으로 판단한다.

### 3.2 Neo4j: Context Graph

**설계 방향**

**설계 원칙**

Neo4j를 프로젝트와 업무 객체 사이의 관계를 탐색하기 위한 Graph Store로 활용한다.

#### 선택 근거

프로젝트 경험은 하나의 테이블이나 단일 업무 객체만으로 설명되지 않는다.

예를 들어 하나의 해결 경험은 다음과 같이 연결될 수 있다.

`Project → Issue → Investigation → Decision → Action → Evidence → Business Event → Context → Knowledge`

이러한 관계는 프로젝트와 업무가 증가할수록 복잡해진다.

RDB에서도 JOIN을 이용해 충분히 표현할 수 있지만, 관계의 종류와 탐색 경로가 계속 확장되면 조회 쿼리와 조인 구조가 복잡해질 수 있다.

Graph DB는 이러한 연결 관계를 노드와 엣지로 직접 표현하고, 특정 객체에서 출발하여 연관된 업무 경험을 탐색하는 데 적합하다.

#### 적용 방향

초기 노드 후보:

- Project
- Evidence
- EvidenceVersion
- BusinessEvent
- Issue
- Decision
- Action
- Context
- Knowledge

초기 관계 후보:

| 관계 | 의미 |
|---|---|
| HAS_EVIDENCE | 프로젝트가 증적을 보유 |
| GENERATED_EVENT | 업무 행위로 이벤트 발생 |
| RELATED_TO | 업무 객체 간 연관 |
| INVESTIGATED_BY | 이슈 조사와 담당자 연결 |
| DECIDED_BY | 의사결정과 결정 주체 연결 |
| RESOLVED_BY | 이슈와 해결 작업 연결 |
| SUPPORTED_BY | 판단 및 경험의 증적 근거 |
| DERIVED_FROM | Context가 원본 정보에서 파생 |
| APPROVED_AS | Context가 승인된 Knowledge로 전환 |
| REUSED_IN | Knowledge가 다른 프로젝트에서 활용 |

실제 노드와 관계는 도메인 모델 및 구현 과정에서 확정한다.

#### 데이터 관리 원칙

- MariaDB의 원본 업무 데이터를 대체하지 않는다.
- Graph DB에는 관계 탐색에 필요한 식별자와 최소 속성을 저장한다.
- 상세 업무 데이터는 MariaDB에서 조회한다.
- Graph DB의 데이터는 원본 데이터와 연결할 수 있어야 한다.
- 그래프 데이터의 생성 및 갱신 실패를 감지하고 복구할 수 있어야 한다.
- 사용자 권한과 프로젝트 접근 범위는 검색 결과를 반환하기 전에 검증한다.

#### 대안 비교

| 대안 | 장점 | 한계 및 판단 |
|---|---|---|
| MariaDB JOIN | 추가 인프라 불필요, 기존 데이터 활용 | 관계 탐색이 복잡해질 경우 쿼리 복잡도 증가 |
| Neo4j | 관계 중심 모델링 및 다단계 탐색 | 별도 데이터 동기화와 운영 필요 |
| Elasticsearch | 전문 검색에 강점 | 관계 중심 탐색의 주 저장소로는 목적이 다름 |
| Vector DB | 의미 기반 유사도 검색 | 업무 객체 간 관계 및 권한 관리의 대체재가 아님 |

#### 도입 검증 기준

Neo4j 도입의 타당성은 기술 자체의 장점이 아니라 실제 업무 시나리오를 통해 판단한다.

- 특정 Evidence에서 연관된 Issue와 Decision을 탐색할 수 있는가?
- 특정 Knowledge의 원본 증적과 발생 이벤트를 추적할 수 있는가?
- 여러 프로젝트에 걸친 유사 경험의 관계를 탐색할 수 있는가?
- MariaDB JOIN 기반 조회와 비교했을 때 모델링 및 조회 구조가 개선되는가?
- 그래프 데이터의 정합성과 복구 가능성을 확보할 수 있는가?

실제 검증에서 Neo4j의 도입 효과가 충분하지 않다면 RDB 기반 관계 조회를 유지하는 것도 가능하다.

### 3.3 Spring AI: AI Search and Reasoning

**설계 방향**

**설계 원칙**

PMIS 자체의 AI 기능은 Spring AI를 활용하여 구현한다.

별도의 독립 AI Runtime을 구축하는 것이 아니라 기존 Spring Boot 애플리케이션과 자연스럽게 통합되는 AI 기능을 우선 구현한다.

#### 선택 근거

기존 업무 시스템의 검색은 일반적으로 키워드, 조건 및 식별자 기반 조회에 의존한다.

하지만 조직 경험을 활용하려면 사용자가 과거 업무의 정확한 명칭이나 데이터 구조를 알지 못하더라도 자연어로 관련 경험을 찾을 수 있어야 한다.

예를 들어 다음과 같은 질문이 가능해야 한다.

- 이전 프로젝트에서 비슷한 JEUS 구성 문제가 발생한 사례가 있는가?
- 해당 문제는 어떤 원인으로 발생했으며 어떻게 해결했는가?
- 해결 과정에서 어떤 변경과 검증이 수행되었는가?
- 현재 프로젝트에 적용할 때 주의해야 할 조건은 무엇인가?

이러한 요구에는 자연어 질의 해석, 관계 탐색, 원본 데이터 조회, 결과 종합 및 출처 제시가 필요하다.

Spring AI는 Spring 기반 애플리케이션에서 모델 연동, 프롬프트 구성, 검색 및 RAG 관련 기능을 구현할 수 있는 프레임워크이므로 PMIS와의 통합에 적합하다.

#### 적용 방향

기본 처리 흐름:

1. 사용자가 자연어 질문을 입력한다.
2. Spring AI가 질문의 의도와 검색 조건을 분석한다.
3. Neo4j에서 관련 업무 객체와 관계를 탐색한다.
4. MariaDB에서 원본 업무 데이터와 승인된 Knowledge를 조회한다.
5. 사용자 권한과 프로젝트 접근 범위를 검증한다.
6. 관련 원본과 근거를 Context로 구성한다.
7. LLM이 검색된 근거를 바탕으로 답변을 생성한다.
8. 답변에 사용된 출처와 관련 업무 객체를 제공한다.

필요한 경우 Vector Search를 보완적으로 활용할 수 있다.

단, 모든 문서를 무조건 벡터화하지 않고 실제 검색 요구와 데이터 특성을 확인한 후 적용한다.

#### 대안 비교

| 대안 | 장점 | 판단 |
|---|---|---|
| Spring AI | 기존 Spring Boot와 통합 용이 | 채택 |
| 별도 AI Runtime | 여러 시스템의 AI 실행을 중앙화 가능 | 현재 PMIS 범위에서 제외 |
| 모델 API 직접 호출 | 초기 구현 단순 | 검색, 프롬프트 및 모델 관리 기능을 직접 구현해야 함 |
| 외부 독립 AI 플랫폼 | 다양한 시스템과 통합 가능 | 현재 Feature에는 과도한 구성 |

#### 설계 결과

Spring AI는 AI 기능을 구현하는 애플리케이션 프레임워크다.

업무 데이터의 소유권이나 승인 권한을 갖지 않으며, MariaDB 및 Neo4j의 데이터를 검색하고 분석하는 역할을 수행한다.

### 3.4 AI Output ≠ Approved Knowledge

**설계 방향**

**설계 원칙**

AI가 생성한 답변이나 요약을 자동으로 공식 Knowledge로 확정하지 않는다.

#### 선택 근거

LLM은 검색된 자료를 바탕으로 유용한 분석을 제공할 수 있지만, 다음과 같은 위험이 존재한다.

- 원본에 없는 내용을 생성할 가능성
- 중요한 조건이나 예외 사항을 누락할 가능성
- 서로 다른 프로젝트의 조건을 동일하게 해석할 가능성
- 과거의 해결 방법을 현재 환경에 부적절하게 적용할 가능성
- 근거가 불충분한 결론을 확정적으로 표현할 가능성

따라서 AI가 생성한 결과와 조직이 검증한 경험은 명확하게 구분해야 한다.

#### 적용 방향

AI가 생성한 결과는 다음과 같은 형태로 활용한다.

- Context 초안
- Knowledge 후보
- 유사 사례 분석 결과
- 기존 Knowledge의 보완 제안
- 추가 검토가 필요한 항목

AI가 생성한 결과는 승인 절차를 거치기 전까지 공식 Knowledge로 취급하지 않는다.

#### 승인 책임

- 작성자는 원본 근거와 경험의 정확성을 확인한다.
- 검토자는 업무 적용 가능성과 예외 조건을 검증한다.
- 승인자는 조직에서 재사용 가능한 지식으로 인정할지 결정한다.
- AI는 검색, 분석 및 초안 작성만 지원한다.

#### 설계 결과

AI의 생산성과 조직 지식의 신뢰성을 분리한다.

AI가 빠르게 후보를 생성할 수 있도록 하되, 조직의 공식 지식으로 전환하는 책임은 사람에게 둔다.

### 3.5 Approved Knowledge Only

**설계 방향**

**설계 원칙**

검토 및 승인된 Knowledge만 조직의 재사용 가능한 경험으로 인정한다.

#### 선택 근거

모든 경험이 모든 프로젝트에 동일하게 적용되는 것은 아니다.

동일한 기술적 문제라도 다음 조건에 따라 해결 방법이 달라질 수 있다.

- 시스템 구성 및 버전
- 인프라 및 네트워크 환경
- 업무 정책 및 보안 기준
- 기술적 제약
- 조직별 운영 절차
- 적용 당시의 전제 조건

따라서 단순히 과거 해결 사례를 보관하는 것만으로는 신뢰할 수 있는 경험 재사용이 어렵다.

Knowledge에는 해결 방법뿐 아니라 적용 조건, 판단 근거, 결과 및 한계가 함께 기록되어야 한다.

#### 적용 방향

Knowledge 생명주기 예시:

`DRAFT → REVIEW → APPROVED → DEPRECATED`

상태별 책임:

| 상태 | 의미 |
|---|---|
| DRAFT | 작성 또는 AI 생성 후보 |
| REVIEW | 정확성 및 적용 가능성 검토 |
| APPROVED | 검토 및 승인 완료 |
| DEPRECATED | 기존 지식의 유효성이 상실되어 사용 중단 |

Knowledge에는 다음 정보를 연결한다.

- 원본 프로젝트
- 관련 Business Event
- 관련 Issue 및 Decision
- 수행한 Action
- 근거 Evidence
- 검증 결과
- 작성자 및 검토자
- 승인자 및 승인 일시
- 적용 조건
- 제한 사항 및 예외 조건

#### 재사용 원칙

다른 프로젝트에서 Knowledge를 검색할 때는 승인 상태만 확인하는 것으로 충분하지 않다.

현재 프로젝트의 환경과 기존 Knowledge의 적용 조건을 비교해야 한다.

또한 Knowledge가 승인되었다는 사실이 현재 상황에 대한 무조건적인 적용 허가를 의미하지는 않는다.

#### 설계 결과

개인의 경험을 조직의 자산으로 전환하되, 그 과정에서 정확성, 출처 및 적용 가능성을 관리한다.

## 4. 통합 아키텍처 원칙

다섯 가지 원칙은 독립적으로 동작하는 것이 아니라 서로 연결되어 데이터 신뢰성과 경험 재사용을 보장한다.

| 구성 요소 | 책임 | 책임지지 않는 영역 |
|---|---|---|
| MariaDB | 업무 원본 데이터 및 트랜잭션 | 관계 중심 탐색 최적화 |
| Neo4j | 업무 객체 간 관계 및 경로 탐색 | 업무 원본의 최종 소유권 |
| Spring AI | 자연어 검색, 분석, 추론 및 응답 생성 | 업무 데이터 승인 및 임의 변경 |
| Context | 이벤트와 원본 자료, 판단 및 결과의 연결 | 검증되지 않은 경험의 공식 승인 |
| Knowledge | 승인된 경험의 관리 및 재사용 | 현재 프로젝트에 대한 무조건적인 적용 |

전체 구조:

```text
                    User
                     |
                     v
              React Frontend
                     |
                     v
               Spring Boot
                     |
          +----------+----------+
          |          |          |
          v          v          v
       MariaDB    Neo4j     Spring AI
       (Source    (Context  (Search &
        of Truth)  Graph)    Reasoning)
          |          |          |
          +----------+----------+
                     |
                     v
             Context Assembly
                     |
                     v
             Permission Check
                     |
                     v
               LLM Response
                     |
                     v
          Source References & Results
```

위 구조는 논리적 책임을 표현한 개념도이며, 실제 호출 순서와 트랜잭션 및 동기화 구조는 상세 설계 단계에서 확정한다.

## 5. 데이터 신뢰성 및 보안 원칙

### 5.1 원본 데이터 우선

AI 검색 결과, 그래프 데이터 및 Context 정보는 원본 업무 데이터와 연결되어야 한다.

원본 데이터가 수정되거나 삭제된 경우 관계 데이터와 검색 결과의 유효성을 확인할 수 있어야 한다.

### 5.2 출처 추적

Knowledge와 AI 응답은 관련 원본 업무 객체를 추적할 수 있어야 한다.

최소한 다음 정보의 연결을 고려한다.

- Project ID
- Business Event ID
- Evidence ID
- Evidence Version ID
- Context ID
- Knowledge ID

### 5.3 접근 권한 통제

검색 단계에서 사용자의 권한과 프로젝트 접근 범위를 확인한다.

특히 Neo4j에서 탐색된 관계를 통해 원래 접근할 수 없는 프로젝트의 정보가 노출되지 않도록 해야 한다.

AI에게 데이터를 전달하기 전에도 접근 권한을 검증한다.

### 5.4 데이터 동기화 및 복구

MariaDB와 Neo4j는 서로 다른 저장소이므로 데이터 정합성 관리가 필요하다.

초기 구현에서는 도메인 변경과 그래프 데이터 반영을 구분하고, 실패 상황에서 재처리할 수 있는 구조를 검토한다.

필요성이 확인되면 Outbox Pattern 등을 적용한다.

단, 초기부터 전체 시스템에 분산 이벤트 아키텍처를 도입하지 않는다.

## 6. 대안 및 범위 제외

이번 Feature는 기존 PMIS의 업무 도메인을 유지하면서 경험 재사용 기능을 단계적으로 확장하는 것을 목표로 한다.

따라서 다음 항목은 현재 범위에서 제외한다.

| 제외 항목 | 제외 이유 |
|---|---|
| PMIS 전체 Event Sourcing 전환 | 기존 업무 시스템의 변경 범위와 복잡도 증가 |
| 모든 업무 데이터를 Neo4j로 이전 | 원본 데이터 책임과 정합성 복잡화 |
| 별도 AI Runtime 구축 | PMIS 자체 AI 기능 검증이 우선 |
| 물류 AI 프로젝트 통합 | 현재 Feature의 목적과 범위 분리 |
| 전체 문서의 무조건적인 Vectorization | 검색 목적과 데이터 특성에 따른 선별 필요 |
| AI 자동 Knowledge 승인 | 조직 지식의 검증 책임과 신뢰성 확보 필요 |
| AI의 무단 업무 데이터 변경 | 업무 권한 및 책임 통제 필요 |

## 7. 설계 리스크 및 검증 항목

| 리스크 | 영향 | 대응 및 검증 방향 |
|---|---|---|
| MariaDB와 Neo4j 정합성 불일치 | 잘못된 관계 탐색 | 동기화 상태 및 재처리 검증 |
| 그래프 데이터 중복 | 데이터 관리 복잡도 증가 | 식별자와 최소 속성 중심 설계 |
| 권한 검증 누락 | 프로젝트 정보 유출 | 검색 결과 반환 전 접근 권한 검증 |
| AI 환각 | 잘못된 경험 전달 | 근거 기반 응답 및 출처 제공 |
| 오래된 Knowledge | 부적절한 경험 재사용 | 적용 조건 및 Deprecated 정책 |
| Neo4j 도입 효과 부족 | 운영 비용 증가 | RDB 기반 조회와 비교 검증 |
| 모델 및 API 의존성 | AI 기능 변경 비용 증가 | Spring AI 추상화 활용 및 모델 교체 가능성 검토 |

## 8. 구현 단계와 설계 검증

본 Feature는 다음 순서로 단계적으로 구현한다.

| 단계 | 구현 내용 | 주요 검증 |
|---|---|---|
| 1 | Evidence Version Restore | 삭제된 버전 복원, 권한 및 원본 보존 |
| 2 | Business Event | 주요 업무 행위의 사실 기록 및 이력 추적 |
| 3 | Context / Knowledge | 이벤트와 근거 연결, 승인 생명주기 |
| 4 | Neo4j Context Graph | 관계 모델 및 탐색 효과 검증 |
| 5 | Spring AI Graph Search | 자연어 검색, 근거 및 권한 검증 |
| 6 | 통합 테스트 및 문서화 | 전체 경험 재사용 흐름 검증 |

각 단계는 독립적으로 설계하고 테스트한 후 다음 단계로 진행한다.

구현 결과가 설계와 달라지는 경우 본 문서와 관련 ADR을 함께 갱신한다.

## 9. 최종 설계 방향

본 Feature의 핵심은 특정 기술의 도입이 아니라 업무 경험이 신뢰할 수 있는 조직 지식으로 전환되는 구조를 만드는 것이다.

이를 위해 다음 책임을 명확히 분리한다.

- MariaDB는 업무 데이터의 원본을 관리한다.
- Business Event는 실제 업무 행위를 기록한다.
- Context는 관련 경험과 근거를 연결한다.
- Neo4j는 업무 객체와 경험 간 관계를 탐색한다.
- Spring AI는 검색과 분석을 지원한다.
- Knowledge는 검토 및 승인된 경험을 관리한다.
- 사람은 경험의 정확성과 재사용 가능성을 판단한다.

궁극적으로 다음 흐름을 구현하고 검증하는 것이 목표다.

`Event → Context → Knowledge → Reuse`

이를 통해 담당자가 변경되더라도 이전 업무의 사실과 판단 근거, 해결 과정 및 결과를 이어받아 더 높은 수준의 업무를 수행할 수 있는 기반을 마련한다.
