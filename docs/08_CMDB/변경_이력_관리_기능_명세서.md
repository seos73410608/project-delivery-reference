# CMDB CI History 기능 명세서

- **문서 유형:** Functional Specification
- **기능:** CMDB Configuration Item Change History
- **대상 시스템:** PMIS
- **대상 도메인:** CMDB
- **구현 브랜치:** `feature/cmdb-ci-history`
- **문서 버전:** 0.6
- **기준일:** 2026-11-17
- **상태:** 기능 명세 확정안

---

## 1. 목적

CI History는 CMDB Configuration Item(CI)의 생성, 속성 변경 및 상태 변경 내역을 기록하고 조회하기 위한 기능이다.

본 기능은 CI의 변경 사실과 변경 전후 값을 추적하여 다음 목적을 달성한다.

1. CI 변경 이력의 추적 가능성 확보
2. 변경자 및 변경 시점 확인
3. 변경 전후 데이터 비교
4. CMDB 데이터 변경의 무결성 확보
5. 운영 및 프로젝트 관리 과정에서 변경 증적 제공

CI History는 업무 데이터의 변경 이력을 기록하는 기능이며, 기록의 법적 보존 기간 및 파기 절차를 관리하는 기능은 포함하지 않는다.

## 2. 기능 범위

### 2.1 포함 범위

- CI 최초 생성 이력 기록
- 공통 CI 속성 변경 이력 기록
- CI 상태 변경 이력 기록
- CI 유형별 상세정보 변경 이력 기록
- 변경자 ID 및 이름 스냅샷 기록
- 변경 전후 값 저장
- CI 단위 이력 목록 조회
- 개별 이력 상세 조회
- 변경 이력 무결성 및 트랜잭션 관리
- 동시성 제어 및 변경 충돌 처리

### 2.2 초기 구현 대상

초기 구현 범위는 `all_types`로 한다.

다음 정보를 모두 대상으로 한다.

- ConfigurationItem 공통 속성
- CI 상태
- CI 유형별 상세정보
- 향후 추가되는 CI 유형별 상세정보

특정 유형인 ServerDetail에 한정하지 않는다.

### 2.3 제외 범위

다음 기능은 초기 CI History 구현 범위에서 제외한다.

- 이력 보존 기간 설정
- 법령 및 내부 규정별 보존 기준 관리
- 별도 저장소로의 이력 데이터 이관
- Legal Hold 관리
- 보존 기간 만료 대상의 자동 파기
- 파기 심사 및 승인
- 파기 실행 및 결과 증적 관리
- 이력 데이터의 직접 수정 및 삭제 기능

해당 기능은 별도 ORDB 시스템에서 관리한다.

## 3. 용어 정의

| 용어 | 설명 |
|---|---|
| CI | Configuration Item |
| CI History | CI 변경 이벤트의 기록 |
| History Event | 하나의 변경 작업으로 생성된 이력 헤더 |
| History Detail | 변경된 개별 속성의 이전 값과 이후 값 |
| Attribute Definition | CI 속성의 명칭, 유형, 그룹 및 표시 순서를 정의하는 메타데이터 |
| attribute_key | 속성을 식별하는 변경 불가능한 고유 키 |
| Actor | 변경 작업을 수행한 사용자 |
| Snapshot | 변경 당시의 사용자 이름 등 시점 정보를 보존한 값 |
| ORDB | Operational Record Database. 기록의 보존·보호·파기 생명주기를 관리하는 별도 시스템 |

## 4. 이벤트 유형

초기 이벤트 유형은 다음과 같이 정의한다.

| 이벤트 유형 | 코드 | 설명 |
|---|---|---|
| 생성 | CREATED | CI 최초 생성 |
| 일반 변경 | UPDATED | 공통 속성 또는 유형별 상세정보 변경 |
| 상태 변경 | STATUS_CHANGED | CI 상태 변경 |

### 4.1 CREATED

CI가 최초 생성될 때 기록한다.

- 생성된 CI의 초기 속성값을 기록한다.
- 최초 생성 시점의 사용자 정보를 기록한다.
- 유형별 상세정보가 함께 생성되는 경우 해당 상세정보도 생성 이력에 포함한다.
- CI 생성 작업과 이력 생성은 하나의 트랜잭션으로 처리한다.

### 4.2 UPDATED

CI의 일반 속성이 변경될 때 기록한다.

대상은 다음과 같다.

- 공통 CI 속성
- CI 유형별 상세정보
- 향후 추가되는 CI 유형별 속성

실제로 값이 변경된 속성만 기록한다.

### 4.3 STATUS_CHANGED

CI 상태가 변경될 때 기록한다.

- 변경 전 상태
- 변경 후 상태
- 변경자
- 변경 일시

일반 속성 변경과 상태 변경이 하나의 요청에서 동시에 발생하면 별도 이벤트로 기록한다.

예를 들어 일반 속성과 상태가 함께 변경된 경우 다음과 같이 처리한다.

- UPDATED 이벤트 1건
- STATUS_CHANGED 이벤트 1건

두 이벤트는 하나의 트랜잭션에서 함께 생성한다.

## 5. 변경 이력 생성 규칙

### 5.1 변경 대상

CI History는 다음 데이터의 변경을 추적한다.

1. ConfigurationItem 공통 속성
2. CI 상태
3. CI 유형별 상세정보
4. Attribute Definition에 등록된 관리 대상 속성

### 5.2 변경값 기록

변경 상세에는 다음 정보를 포함한다.

- attribute_key
- 변경 전 값
- 변경 후 값
- 필요 시 값의 데이터 유형

실제 변경이 발생한 속성만 상세 이력으로 생성한다.

변경 전후 값이 동일하면 이력을 생성하지 않는다.

### 5.3 NULL 및 빈 문자열

다음 상태는 서로 구분한다.

- NULL
- 빈 문자열
- 실제 문자열 값

NULL과 빈 문자열을 동일한 값으로 취급하지 않는다.

### 5.4 값의 데이터 유형

변경값은 원래 속성의 데이터 유형을 보존할 수 있어야 한다.

초기 지원 대상 데이터 유형은 다음과 같다.

| 유형 | 설명 |
|---|---|
| STRING | 문자열 |
| NUMBER | 숫자 |
| BOOLEAN | 참/거짓 |
| DATE | 날짜 |
| DATETIME | 날짜 및 시간 |
| OBJECT | 구조화된 객체 |
| ARRAY | 배열 |

실제 DB 저장 형식 및 직렬화 규칙은 DB 설계 단계에서 확정한다.

### 5.5 변경 이벤트 생성 조건

- 실제 데이터 변경이 발생한 경우에만 이벤트를 생성한다.
- 변경 대상이 없거나 모든 값이 기존 값과 동일하면 이벤트를 생성하지 않는다.
- 변경 이벤트와 상세 변경 내역은 함께 생성되어야 한다.
- 이벤트 헤더만 존재하고 상세 변경 내역이 누락되는 상태를 허용하지 않는다.

## 6. 변경자 정보 관리

변경자 정보는 사용자 ID와 변경 당시 이름 스냅샷을 함께 보관한다.

| 필드 | 설명 |
|---|---|
| changed_by | 변경자 User ID 참조 |
| changed_by_name | 변경 당시 사용자 이름 스냅샷 |

### 6.1 변경자 정보 생성

- 변경자 정보는 인증된 사용자 정보를 기준으로 백엔드에서 결정한다.
- 클라이언트에서 전달한 사용자 ID 또는 이름을 신뢰하지 않는다.
- 인증된 principal의 사용자 ID를 기준으로 사용자 정보를 확인한다.
- 변경 당시 사용자 이름을 스냅샷으로 저장한다.

### 6.2 스냅샷 유지

사용자 이름이 변경되거나 계정이 비활성화 또는 삭제되더라도 과거 이력의 changed_by_name은 변경하지 않는다.

사용자 인증 정보나 비밀번호 등 민감한 인증 데이터는 이력에 저장하지 않는다.

## 7. Attribute Definition 연계

### 7.1 기본 원칙

CI History의 속성 표시는 Attribute Definition을 기준으로 처리한다.

변경 이력은 속성의 안정적인 식별자인 `attribute_key`를 기준으로 저장하고, 화면 표시 정보는 현재 Attribute Definition을 기준으로 조회한다.

### 7.2 주요 속성 정의 항목

| 항목 | 설명 |
|---|---|
| attribute_key | 속성의 고유 식별자 |
| display_name | 화면 표시 명칭 |
| node_type | GROUP 또는 FIELD |
| data_type | 속성 데이터 유형 |
| display_format | 표시 형식 |
| display_order | 표시 순서 |
| parent_id | 상위 그룹 참조 |
| ci_type_id | 적용 CI 유형 |
| enabled | 사용 여부 |
| description | 속성 설명 |

### 7.3 표시 정책

- 속성명은 현재 Attribute Definition의 display_name을 사용한다.
- 그룹 구조는 현재 Attribute Definition을 사용한다.
- 표시 순서는 현재 Attribute Definition의 display_order를 사용한다.
- 변경 전후 값은 History에 저장된 값을 사용한다.

따라서 속성의 표시명, 그룹 또는 표시 순서가 변경되면 과거 이력 화면에도 현재 정의가 반영된다.

단, 과거 변경 기록 자체의 attribute_key와 변경값은 수정하지 않는다.

### 7.4 attribute_key 관리

`attribute_key`는 이력 데이터와 Attribute Definition을 연결하는 안정적인 식별자다.

- 생성 후 변경하지 않는 것을 원칙으로 한다.
- 기존 키를 임의로 변경하거나 삭제하지 않는다.
- 불가피한 변경이 필요한 경우 별도의 마이그레이션 및 호환성 처리 절차를 거친다.

## 8. Attribute Definition 상속 정책

CI 유형별 속성 정의는 상속 구조를 적용한다.

### 8.1 최종 적용 속성 구성

특정 CI 유형에 적용되는 최종 속성은 다음 세 가지의 합집합이다.

1. 전역 공통 속성
2. 상위 CI 유형으로부터 상속된 속성
3. 해당 CI 유형에 직접 정의된 속성

### 8.2 상속 규칙

- 전역 공통 속성은 모든 CI 유형에 적용한다.
- 하위 CI 유형은 상위 유형의 속성을 상속한다.
- 하위 유형은 상위 유형의 속성을 재정의하지 않는다.
- 상위 유형의 속성 정의 변경은 하위 유형에도 반영한다.
- 하위 유형만의 고유 속성은 해당 하위 유형에 직접 정의한다.
- 적용 가능한 상속 계층 전체에서 attribute_key는 중복될 수 없다.

### 8.3 데이터 저장 위치

Attribute Definition 상속은 메타데이터의 적용 범위를 결정하는 규칙이다.

실제 CI 속성값은 다음 위치에서 관리한다.

- 공통 CI 속성: ConfigurationItem
- 유형별 상세 속성: 각 CI 유형별 상세 엔티티 및 테이블

Attribute Definition의 상속 자체가 실제 CI 데이터를 복제하거나 상속하는 것을 의미하지 않는다.

초기 구현에서는 속성 재정의 기능을 제공하지 않는다.

## 9. CI History 조회 정책

### 9.1 조회 범위

이력 조회는 특정 CI 단위로 수행한다.

특정 CI를 조회할 때 해당 CI에 속한 이력만 반환한다.

초기 범위에서는 전체 CI의 통합 이력 검색 기능을 제공하지 않는다.

### 9.2 이력 목록

이력 목록은 다음 항목을 제공한다.

| 항목 | 설명 |
|---|---|
| history_id | 이력 ID |
| event_type | 이벤트 유형 |
| changed_by_name | 변경 당시 사용자 이름 |
| changed_at | 변경 일시 |
| changed_field_count | 변경된 속성 수 |
| change_summary | 변경 요약 |

### 9.3 정렬

기본 정렬은 최신순이다.

1. changed_at 내림차순
2. changed_at이 동일하면 history_id 내림차순

### 9.4 검색 조건

다음 조건으로 이력을 검색할 수 있다.

- 이벤트 유형
- 변경자
- 시작 일시
- 종료 일시

검색 조건은 선택적으로 적용할 수 있다.

시작 일시와 종료 일시를 함께 지정하는 경우 시작 일시는 종료 일시보다 늦을 수 없다.

### 9.5 페이징

기존 PMIS의 공통 페이징 및 검색 규칙을 따른다.

이력 목록은 이벤트 헤더와 변경된 속성 수를 제공한다.

개별 속성의 변경 전후 값은 상세 조회 API에서 제공한다.

## 10. CI History 상세 조회

개별 이력 상세 조회에서는 다음 정보를 제공한다.

### 10.1 기본 정보

- History ID
- CI ID
- 이벤트 유형
- 변경자 ID
- 변경 당시 사용자 이름
- 변경 일시
- 변경 요약

### 10.2 변경 상세 정보

각 변경 속성에 대해 다음 정보를 제공한다.

- attribute_key
- 현재 Attribute Definition의 display_name
- 현재 Attribute Definition의 그룹 정보
- 변경 전 값
- 변경 후 값
- 데이터 유형 및 표시 형식

변경 상세는 History에 저장된 값과 현재 Attribute Definition의 표시 정보를 조합하여 반환한다.

Attribute Definition을 찾을 수 없는 경우에도 저장된 attribute_key와 변경값을 식별할 수 있도록 처리해야 한다. 이 경우 화면에는 정의되지 않은 속성임을 구분할 수 있는 대체 표시를 제공한다.

## 11. 동시성 제어

CI 변경 작업은 JPA Optimistic Lock을 적용한다.

### 11.1 적용 범위

- ConfigurationItem 공통 속성 변경
- CI 상태 변경
- CI 유형별 상세정보 변경

### 11.2 Aggregate Version

유형별 상세정보만 변경하는 경우에도 CI Aggregate의 버전을 확인하고 증가시켜야 한다.

이를 통해 공통 CI와 상세정보 사이의 동시 변경 충돌을 감지한다.

### 11.3 충돌 처리

다른 요청에서 먼저 변경이 완료되어 버전이 일치하지 않으면 다음과 같이 처리한다.

- HTTP 409 Conflict 반환
- 명시적인 비즈니스 오류 코드 제공
- CI 변경 작업 롤백
- CI History 생성 취소

동시성 충돌로 인해 실제 변경 없이 이력만 생성되는 상황을 허용하지 않는다.

## 12. 트랜잭션 및 무결성

CI 변경과 CI History 생성은 동일한 트랜잭션에서 처리한다.

### 12.1 원자성

다음 작업은 하나의 트랜잭션으로 처리한다.

1. 기존 CI 값 조회
2. 변경 대상 및 변경값 검증
3. 동시성 버전 확인
4. CI 데이터 변경
5. History Event 생성
6. History Detail 생성

일부 작업이라도 실패하면 전체 트랜잭션을 롤백한다.

### 12.2 무결성 원칙

- History Event는 유효한 CI에 연결되어야 한다.
- History Detail은 유효한 History Event에 연결되어야 한다.
- 변경자 정보는 인증된 사용자 기준으로 생성되어야 한다.
- History 데이터는 생성 이후 직접 수정하지 않는다.
- 일반 업무 API에서 History를 직접 삭제하지 않는다.

## 13. CI 삭제 정책

초기 구현에서는 CI의 Soft Delete 기능을 제공하지 않는다.

CI History가 존재하는 CI의 물리적 삭제는 금지한다.

- 이력이 존재하는 CI는 물리적으로 삭제할 수 없다.
- History Event를 직접 수정하거나 삭제할 수 없다.
- History Detail을 직접 수정하거나 삭제할 수 없다.

향후 Soft Delete, DELETED 이벤트, 복구 기능은 별도 기능으로 검토한다.

## 14. ORDB 연계 및 책임 분리

### 14.1 기본 원칙

CI History와 ORDB는 별도의 시스템 및 데이터베이스로 설계한다.

두 영역은 목적과 책임이 다르다.

| 구분 | CI History | ORDB |
|---|---|---|
| 목적 | CI 변경 사실 추적 | 기록 생명주기 관리 |
| 핵심 데이터 | 변경 이벤트 및 상세 | 기록 분류, 보존 정책, 파기 정보 |
| 주요 기능 | 생성, 조회, 변경 추적 | 보존, 보호, 심사, 승인, 파기 |
| 운영 책임 | CMDB | 별도 운영 기록 관리 영역 |

### 14.2 CI History 책임

CI History는 다음 책임을 가진다.

- CI 변경 이벤트 생성
- 변경 전후 값 기록
- 변경자 및 변경 일시 기록
- 이력 조회
- 변경 이력 무결성 유지
- 안정적인 이력 식별자 제공

### 14.3 ORDB 책임

ORDB는 별도 설계 및 구현 대상으로 한다.

향후 ORDB에서 관리할 주요 기능은 다음과 같다.

- 기록 분류 및 관리 대상 등록
- 보존 정책 및 법적 근거 관리
- 고객사 내부 규정별 보존 기준 관리
- 보존 기간 및 만료 대상 관리
- 별도 보존 저장소 관리
- Legal Hold
- 파기 심사 및 승인
- 파기 실행 및 결과 증적
- 운영 감사 이력

### 14.4 연계 원칙

- CI History는 변경 이력의 원본 시스템으로 유지한다.
- ORDB는 CI History의 안정적인 이력 식별자를 참조할 수 있어야 한다.
- 업무 데이터와 기록 관리 데이터의 책임을 혼합하지 않는다.
- ORDB가 별도 보존 데이터를 필요로 하는 경우 저장·이관 방식은 별도 아키텍처에서 결정한다.
- ORDB의 보존 정책 및 파기 판단을 CI History 내부에 중복 구현하지 않는다.

### 14.5 보존 및 파기 관련 유의사항

모든 CI History에 동일한 법정 보존 기간이 자동 적용되는 것으로 간주하지 않는다.

실제 보존 의무는 기록의 성격, 적용 법령, 고객사 내부 규정, 계약 및 개인정보 관련 의무 등을 검토하여 결정해야 한다.

CI History 초기 구현에서는 보존 기간 계산이나 자동 파기 기능을 제공하지 않는다.

## 15. 서비스 책임 및 구현 원칙

### 15.1 생성 책임

CI 생성 및 변경을 수행하는 백엔드 서비스가 History 생성을 책임진다.

History 생성 로직은 공통 서비스 계층에서 재사용할 수 있도록 구성한다.

CI 생성이 공통 생성 서비스를 통해 이루어지는 경우 해당 공통 서비스에서 생성 이력을 한 번만 기록한다.

CI 유형별 등록 서비스에서 동일한 생성 이력을 중복 생성하지 않는다.

### 15.2 변경 책임

CI 공통 속성, 상태 및 유형별 상세정보의 변경 서비스는 변경 전후 값을 비교하여 History를 생성해야 한다.

변경 서비스가 History 생성 책임을 우회하지 않도록 서비스 구조를 설계한다.

### 15.3 조회 책임

History 조회 서비스는 다음 책임을 가진다.

- CI별 이력 목록 조회
- 검색 조건 적용
- 페이징 및 정렬
- 개별 이력 상세 조회
- Attribute Definition 표시 정보 결합

## 16. 권한 및 접근 통제

초기 구현은 PMIS의 기존 인증 및 권한 체계를 따른다.

- 인증된 사용자만 이력을 조회할 수 있다.
- CI 조회 권한이 없는 사용자는 해당 CI의 이력을 조회할 수 없다.
- History 직접 수정 및 삭제 API는 제공하지 않는다.
- 변경자 정보는 인증된 사용자로부터 결정한다.

세부 역할별 조회 제한과 운영 감사 권한은 기존 PMIS 권한 정책과 함께 검토한다.

## 17. 오류 처리

| 상황 | HTTP | 처리 |
|---|---:|---|
| CI 없음 | 404 | 대상 CI 없음 |
| History 없음 | 404 | 대상 이력 없음 |
| 접근 권한 없음 | 403 | 접근 거부 |
| 동시성 충돌 | 409 | 변경 작업 전체 취소 |
| 잘못된 검색 조건 | 400 | 입력값 검증 오류 |
| Attribute Definition 누락 | 정상 조회 | 대체 표시 처리 |
| History 생성 실패 | 500 또는 공통 오류 정책 | CI 변경 포함 전체 롤백 |

오류 응답은 PMIS 공통 예외 및 응답 형식을 따른다.

## 18. 테스트 요구사항

### 18.1 이벤트 생성

- CI 생성 시 CREATED 이벤트 생성
- 공통 속성 변경 시 UPDATED 이벤트 생성
- 유형별 상세정보 변경 시 UPDATED 이벤트 생성
- 상태 변경 시 STATUS_CHANGED 이벤트 생성
- 일반 속성과 상태 동시 변경 시 이벤트 2건 생성
- 실제 변경이 없으면 이벤트 미생성

### 18.2 변경값 검증

- 변경 전후 값 정상 기록
- NULL과 빈 문자열 구분
- 숫자, Boolean, 날짜, 객체 및 배열 값 처리
- 변경 속성만 상세 내역에 포함

### 18.3 변경자 정보

- 인증된 사용자 ID 기록
- 변경 당시 사용자 이름 스냅샷 기록
- 클라이언트에서 전달한 사용자 정보 무시
- 사용자 이름 변경 후 기존 스냅샷 유지

### 18.4 Attribute Definition

- 공통 속성 적용
- 상위 유형 속성 상속
- 하위 유형 고유 속성 적용
- attribute_key 중복 방지
- 현재 display_name 및 그룹 정보 반영
- 정의되지 않은 attribute_key의 대체 표시

### 18.5 조회

- 특정 CI의 이력만 조회
- 최신순 정렬
- 변경 일시 동률 시 History ID 내림차순
- 이벤트 유형 필터
- 변경자 필터
- 기간 필터
- 페이징
- 상세 변경 내역 조회

### 18.6 동시성 및 트랜잭션

- 공통 CI 동시 변경 충돌
- 상태 변경 동시성 충돌
- 상세정보만 변경하는 경우의 버전 충돌
- 동시성 충돌 시 History 미생성
- History 생성 실패 시 CI 변경 롤백
- 일반 속성과 상태 변경 동시 처리 시 원자성 검증

### 18.7 삭제 및 무결성

- History가 존재하는 CI 물리적 삭제 차단
- History 직접 수정 차단
- History 직접 삭제 차단
- History Event와 Detail 관계 무결성 검증
