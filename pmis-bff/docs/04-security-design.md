# PMIS BFF 보안 설계서

## 1. 문서 목적

본 문서는 PMIS BFF 도입에 따른 인증, 인가, 세션, 쿠키, API 접근 통제 및 보안 정책을 정의한다.

PMIS는 React Frontend, Node.js BFF, Spring Boot Backend로 구성하며, 각 계층의 보안 책임을 분리하여 인증 정보 보호와 비인가 접근 방지를 목적으로 한다.

본 문서는 현재 구현된 보안 구성과 향후 인증·세션 기능 구현을 위한 목표 보안 정책을 구분하여 관리한다.

현재 BFF에는 Backend 로그인 연계, 서버 측 세션 저장소, HttpOnly 인증 쿠키 발급 등의 기능이 구현되어 있다.

다만 인증 세션 조회, 토큰 갱신, 로그아웃, CSRF 방어 및 일반 업무 API 프록시 등은 후속 구현 대상으로 관리한다.

## 2. 보안 설계 기본 원칙

### 2.1 보안 책임 분리

각 애플리케이션은 다음과 같이 보안 책임을 가진다.

| 구성 요소 | 보안 책임 |
|---|---|
| React Frontend | 사용자 입력 처리, 화면 접근 제어, XSS 방지 고려 |
| Node.js BFF | 인증 쿠키, 서버 측 세션 관리, CSRF 및 Origin 검증, API 접근 통제 |
| Spring Boot Backend | 최종 인증·인가 검증, 사용자 상태 및 업무 권한 검증 |
| MariaDB | 데이터 접근 통제 및 계정 권한 관리 |
| 인프라 | 네트워크 접근 통제, TLS, 서버 및 운영 환경 보안 |

BFF는 브라우저와 Backend 사이의 보안 계층을 제공하지만 Spring Boot Backend의 인증·인가 책임을 대체하지 않는다.

Backend는 BFF에서 전달된 요청이라도 인증 정보와 사용자 권한을 독립적으로 검증한다.

### 2.2 브라우저 인증 토큰 비노출

Access Token과 Refresh Token은 BFF 서버 측 세션 저장소에서 관리한다.

브라우저에는 BFF 세션 식별자를 담은 HttpOnly 쿠키를 발급한다.

브라우저의 localStorage 또는 sessionStorage에 Access Token과 Refresh Token을 저장하지 않는다.

JavaScript에서 인증 토큰을 직접 조회하거나 관리하지 않는 구조를 유지한다.

### 2.3 Backend 독립 인증·인가

Spring Boot Backend는 BFF에서 전달된 요청이라도 인증 정보와 사용자 권한을 독립적으로 검증한다.

BFF를 통과했다는 사실만으로 요청을 신뢰하지 않는다.

Backend는 JWT 유효성, 사용자 상태, 업무 권한 및 데이터 접근 권한을 최종적으로 판단한다.

### 2.4 최소 권한 원칙

사용자, 애플리케이션 및 데이터베이스 계정에는 업무 수행에 필요한 최소 권한만 부여한다.

운영 환경에서 BFF와 Backend 간 통신 계정 및 데이터베이스 계정도 역할에 따라 권한을 분리한다.

### 2.5 보안 기본값 적용

명시적으로 허용하지 않은 Origin, API 경로, 네트워크 접근 및 인증되지 않은 요청은 기본적으로 차단하는 방향으로 설계한다.

보안 설정이 누락되거나 유효하지 않은 경우 안전하지 않은 기본값으로 자동 전환하지 않는다.

## 3. 보안 아키텍처

### 3.1 목표 보안 아키텍처

│              Browser                │
│                                     │
│  - 인증 토큰 직접 저장 금지          │
│  - HttpOnly Cookie 사용             │
│  - Access Token 비노출              │
│  - Refresh Token 비노출             │
└──────────────────┬──────────────────┘
                   │ HTTPS
                   │
═══════════════════╪════════════════════
       Browser / Server 보안 경계

본 구조는 PMIS의 목표 보안 아키텍처이다.

현재 Backend 로그인 연계, BFF 서버 측 세션 저장 및 HttpOnly 쿠키 발급은 구현되어 있다.

Cookie 기반 인증 검증, CSRF, API Allowlist 및 일반 업무 API 프록시는 후속 구현 대상이다.

### 3.2 보안 통신 원칙

- 브라우저와 서비스 구간은 HTTPS를 사용한다.
- BFF와 Backend 사이의 통신은 내부 네트워크 또는 보호된 통신 구간을 사용한다.
- 외부에서 Backend API에 직접 접근할 수 없도록 네트워크 접근을 제한한다.
- 데이터베이스는 Backend에서만 접근하도록 구성한다.
- 운영 환경의 인증 정보와 비밀 키는 소스 코드 및 Git에 포함하지 않는다.
- Redis 세션 저장소는 허용된 애플리케이션에서만 접근하도록 네트워크 및 인증 정책을 적용한다.

## 4. 인증 및 토큰 보안

### 4.1 인증 처리 구조

목표 인증 흐름은 다음과 같다.

```text
1. 사용자가 로그인 정보 입력
             |
             v
2. React에서 BFF 로그인 API 호출
             |
             v
3. BFF가 Spring Boot 인증 API 호출
             |
             v
4. Spring Boot가 사용자 인증 수행
             |
             v
5. 인증 결과 및 Token 발급
             |
             v
6. BFF가 인증 정보 및 사용자 정보를 서버 측 세션에 저장
             |
             v
7. BFF가 HttpOnly Cookie 발급
             |
             v
8. 브라우저는 쿠키를 이용하여 BFF API 호출
             |
             v
9. BFF가 세션 및 인증 정보를 확인하고 Backend 호출
             |
             v
10. Spring Boot가 JWT 및 권한 최종 검증
```

현재 구현 범위는 다음과 같다.

- BFF 로그인 API에서 Backend 로그인 API 호출
- Backend 로그인 결과 수신
- BFF 서버 측 세션 저장
- `pmis_session` HttpOnly 쿠키 발급
- Backend의 다중 세션 선택 로그인 흐름과 연계

이후 세션 조회, Refresh, Logout 및 인증 미들웨어를 순차적으로 구현한다.

### 4.2 Access Token 관리

Access Token은 Spring Boot Backend가 발급하고 BFF가 관리한다.

BFF는 로그인 성공 시 발급받은 Access Token을 서버 측 세션 저장소에 보관한다.

브라우저의 localStorage 또는 sessionStorage에 Access Token을 저장하지 않는다.

BFF가 Backend API 요청을 수행할 때 필요한 인증 정보를 전달하는 구조를 적용한다.

현재 일반 업무 API 프록시 및 인증 미들웨어는 후속 구현 대상이다.

### 4.3 Refresh Token 관리

Refresh Token은 BFF 서버 측에서 관리한다.

브라우저에 Refresh Token을 직접 전달하거나 JavaScript에서 접근 가능한 저장소에 보관하지 않는다.

토큰 갱신 과정에서는 Backend의 Refresh Token 검증 및 재발급 결과를 확인하고 BFF의 인증 상태를 갱신한다.

Backend의 Refresh Token 회전 정책에 따라 기존 Refresh Token이 폐기되고 새로운 Refresh Token이 발급되는 경우 BFF도 세션에 저장된 토큰을 함께 갱신해야 한다.

토큰 갱신은 동일 세션에서 동시에 여러 요청이 발생하더라도 기존 Refresh Token이 중복 사용되지 않도록 동시 실행 제어를 적용한다.

현재 BFF Refresh API는 후속 구현 대상이다.

### 4.4 JWT 검증 책임

JWT의 최종 검증 책임은 Spring Boot Backend에 있다.

검증 항목은 Backend의 실제 JWT 정책에 따라 다음 사항을 포함하도록 한다.

- JWT 서명 유효성
- 토큰 만료 여부
- 발급자(issuer)
- 대상자(audience)
- 토큰 유형 및 사용 목적
- 사용자 활성 상태
- 업무 권한

실제 검증 항목은 Backend JWT 구현과 일치하도록 관리한다.

BFF는 Refresh Token의 JWT `exp` 값을 세션 TTL 계산에 활용할 수 있다.

이 과정은 JWT 서명 검증이나 인증을 의미하지 않는다.

BFF가 JWT를 직접 검증하는 구조를 추가할 경우 검증 키, 키 교체 및 검증 책임을 별도로 설계해야 한다.

HMAC 방식의 비밀 키를 사용하는 경우 키 공유와 보관 방식을 검토해야 하며, 비대칭 키 방식 적용 여부도 함께 검토한다.

## 5. Cookie 보안

### 5.1 현재 인증 쿠키 정책

현재 BFF에서 발급하는 인증 쿠키의 설정은 다음과 같다.

| 속성 | 현재 구현 | 목적 |
|---|---|---|
| Cookie 이름 | `pmis_session` | BFF 세션 식별 |
| HttpOnly | true | JavaScript의 쿠키 직접 접근 방지 |
| Secure | production 환경에서 true | HTTPS 연결에서만 전송 |
| SameSite | lax | 교차 사이트 요청 제한 |
| Path | `/` | 쿠키 적용 경로 |
| Domain | 미지정 | 불필요한 하위 도메인 공유 방지 |
| Max-Age | 세션 만료 시각 기준 | 쿠키 유효기간 관리 |

현재 쿠키 설정은 `src/auth/session/session-cookie.ts`에서 관리한다.

쿠키에는 BFF 세션 식별자가 저장되며 Access Token과 Refresh Token은 쿠키에 직접 저장하지 않는다.

### 5.2 HttpOnly 적용

HttpOnly 속성을 활성화하여 브라우저 JavaScript에서 인증 쿠키를 직접 읽지 못하도록 한다.

다만 HttpOnly는 XSS 공격 자체를 차단하지 않는다.

악성 스크립트가 실행되면 쿠키 내용을 읽지 못하더라도 브라우저를 통해 인증된 요청을 실행할 수 있으므로 별도의 XSS 방어가 필요하다.

### 5.3 Secure 적용

운영 환경에서는 HTTPS를 사용하고 Secure 속성을 활성화한다.

현재 구현은 `NODE_ENV=production`인 경우 Secure를 활성화한다.

개발 환경의 HTTP 사용은 로컬 테스트에 한정한다.

운영 환경에서 HTTPS가 정상적으로 구성되었는지 확인하고 Secure 설정이 유지되도록 한다.

### 5.4 SameSite 적용

현재 SameSite 값은 `lax`이다.

SameSite 속성은 교차 사이트 요청에서 쿠키 전송을 제한하는 보조 방어 수단으로 사용한다.

SameSite 설정만으로 CSRF 공격에 대한 완전한 방어가 이루어지는 것은 아니므로 Origin 검증 및 CSRF Token 정책을 함께 적용한다.

운영 환경에서 Frontend와 BFF의 도메인 및 배포 구조가 달라지는 경우 SameSite 설정을 재검토한다.

### 5.5 쿠키 만료 정책

현재 쿠키의 Max-Age는 BFF 세션의 만료 시각을 기준으로 계산한다.

BFF 세션의 만료 시각은 Backend Refresh Token의 JWT `exp` 값을 기준으로 설정한다.

쿠키 만료와 서버 측 세션 만료가 일치하도록 관리한다.

브라우저 쿠키가 만료되더라도 서버 측 세션이 남아 있을 수 있으므로 서버 측 세션의 만료 및 삭제 처리를 별도로 수행해야 한다.

### 5.6 쿠키 서명 정책

현재 `@fastify/cookie` 플러그인은 등록되어 있으나 서명용 Secret을 설정한 상태는 아니다.

현재 쿠키는 서버 측 세션을 조회하기 위한 식별자로 사용한다.

쿠키 서명 기능을 추가하는 경우 Secret 관리, 키 교체 및 서명 검증 정책을 별도로 설계한다.

쿠키 서명은 서버 측 세션의 유효성 검증을 대체하지 않는다.

## 6. CSRF 및 Origin 보안

### 6.1 CSRF 방어 필요성

인증 쿠키는 브라우저가 요청에 자동으로 포함하므로 공격자가 사용자를 유도하여 비정상적인 요청을 전송할 가능성이 있다.

따라서 쿠키 기반 인증 구조에서는 CSRF 방어가 필요하다.

현재 CSRF Token 검증 및 별도 Origin 검증 기능은 구현되지 않았다.

### 6.2 Origin 검증

BFF는 상태를 변경하는 요청에 대해 요청 Origin을 검증한다.

검증 기준은 환경 설정에 정의된 허용 Origin을 사용한다.

허용되지 않은 Origin에서 발생한 요청은 거부한다.

Origin 헤더가 없는 요청이나 형식이 유효하지 않은 요청에 대한 처리 정책도 별도로 정의한다.

현재 CORS 설정은 환경 변수 `FRONTEND_ORIGIN`을 기준으로 허용 Origin을 제한한다.

CORS 설정과 별도의 서버 측 Origin 검증은 구분하여 구현한다.

### 6.3 CSRF Token

CSRF 방어가 필요한 요청에는 CSRF Token 검증을 적용한다.

목표 처리 방식은 다음과 같다.

1. 사용자가 인증된 상태에서 CSRF Token 발급 또는 조회
2. Frontend가 상태 변경 요청에 CSRF Token 포함
3. BFF가 CSRF Token 검증
4. 검증 성공 시 Backend API 호출
5. 검증 실패 시 요청 거부

CSRF Token의 발급 방식, 저장 위치 및 검증 방식은 구현 단계에서 확정한다.

### 6.4 보호 대상 요청

다음과 같은 상태 변경 요청을 주요 보호 대상으로 한다.

- POST
- PUT
- PATCH
- DELETE

GET 요청은 데이터 조회 등 상태 변경이 없는 작업에 사용한다.

GET 요청에서 업무 데이터 변경이나 세션 종료와 같은 상태 변경 작업을 수행하지 않는다.

### 6.5 현재 구현 상태

- CORS 플러그인 등록 완료
- 허용 Origin 환경 변수 적용 완료
- Credential 요청 허용 설정 완료
- 별도 Origin 검증 미구현
- CSRF Token 발급 및 검증 미구현

## 7. CORS 보안

### 7.1 허용 Origin 제한

CORS는 허용된 Frontend Origin만 등록한다.

운영 환경에서 와일드카드 Origin을 사용하지 않는다.

현재 BFF는 `FRONTEND_ORIGIN` 환경 변수로 허용 Origin을 관리한다.

### 7.2 Credential 요청

인증 쿠키를 사용하는 경우 Credential 요청에 대한 허용 정책을 명확히 설정한다.

현재 BFF의 기본 설정은 다음과 같다.

```ts
await app.register(cors, {
  origin: env.frontendOrigin,
  credentials: true,
});
```

### 7.3 운영 환경 적용 기준

운영 환경에서 Frontend와 BFF를 동일 Origin으로 제공하는 경우 CORS 설정이 필요한지 검토한다.

CORS는 브라우저의 교차 출처 접근 제어이며, 인증이나 인가를 대체하지 않는다.

허용 Origin 설정만으로 CSRF 방어가 완료되는 것은 아니다.

## 8. Backend API 접근 통제

### 8.1 API Allowlist

BFF는 사전에 허용된 Backend API만 호출한다.

사용자 요청으로 전달된 임의의 URL을 Backend 호출 대상으로 사용하지 않는다.

API별 호출 경로와 허용 HTTP Method를 명시적으로 관리한다.

현재 BFF는 Backend 로그인 및 세션 선택 로그인 API 연계가 구현되어 있다.

일반 업무 API에 대한 Allowlist 및 프록시 기능은 후속 구현 대상이다.

### 8.2 SSRF 방어

BFF에서 외부 또는 내부 URL을 동적으로 호출하는 기능을 제한한다.

다음 원칙을 적용한다.

- Backend 기본 주소는 환경 설정으로 관리한다.
- 사용자 입력 URL을 그대로 호출하지 않는다.
- API 경로는 사전에 정의된 목록을 사용한다.
- 호출 가능한 HTTP Method를 제한한다.
- Backend 이외의 임의 목적지로 요청이 전달되지 않도록 한다.

### 8.3 Backend 독립 검증

Spring Boot Backend는 BFF에서 전달된 요청에 대해서도 다음 항목을 검증한다.

- 인증 여부
- 사용자 활성 상태
- 사용자 권한
- 요청 데이터 유효성
- 업무 규칙
- 데이터 접근 권한

BFF의 요청 검증만으로 Backend의 검증을 생략하지 않는다.

## 9. 세션 보안

### 9.1 세션 관리 원칙

PMIS는 사용자별 활성 세션을 식별하고 관리하는 구조를 적용한다.

세션은 사용자 단위가 아닌 개별 로그인 단위로 구분한다.

각 세션은 고유 식별자를 가지며 개별 세션의 생성, 조회, 갱신 및 종료를 관리할 수 있어야 한다.

현재 BFF는 고유 세션 식별자를 발급하고 서버 측 세션 저장소에 세션 정보를 저장하는 구조를 구현했다.

### 9.2 사용자별 최대 동시 세션 수

사용자별 최대 동시 세션 수는 관리자가 설정한다.

최대 세션 수를 초과하는 신규 로그인 요청이 발생하면 기존 세션을 자동으로 종료하지 않는다.

또한 신규 로그인을 무조건 자동 거부하는 방식으로 처리하지 않는다.

다음 절차를 적용한다.

```text
1. 사용자 로그인 요청
          |
          v
2. 사용자 인증 정보 검증
          |
          v
3. 활성 세션 수 확인
          |
          v
4. 최대 세션 수 초과 여부 확인
          |
     ┌────┴────┐
     |         |
   미초과       초과
     |         |
     v         v
  세션 생성   활성 세션 목록 조회
     |         |
     |         v
     |      사용자에게 목록 제공
     |         |
     |         v
     |      종료할 세션 선택
     |         |
     |         v
     |      선택 세션 폐기
     |         |
     └────┬────┘
          |
          v
      신규 세션 생성
          |
          v
       로그인 완료
```

Backend의 사용자별 최대 세션 수 설정 및 세션 선택 로그인 흐름은 구현되어 있다.

### 9.3 세션 종료

사용자가 선택한 세션만 종료한다.

세션 종료 시 다음 항목을 처리해야 한다.

- 해당 세션의 인증 상태 폐기
- 해당 세션과 연결된 Refresh Token 폐기
- 해당 세션을 통한 추가 인증 요청 차단
- 세션 종료 결과 기록

Access Token이 자체적으로 유효기간까지 사용 가능한 구조라면 세션 종료 직후 토큰이 무효화되지 않을 수 있다.

따라서 즉시 세션 폐기가 필요한 경우 Backend에서 세션 상태를 확인하거나 별도의 토큰 폐기 정책을 적용해야 한다.

현재 BFF 세션 종료 API 및 Backend 세션 폐기 연계는 후속 구현 대상이다.

### 9.4 동시 로그인 제어

여러 로그인 요청이 동시에 발생하더라도 사용자별 최대 세션 수를 초과하지 않도록 처리해야 한다.

세션 수 확인과 신규 세션 생성은 원자적으로 처리할 수 있는 구조를 적용한다.

단순히 현재 세션 수를 조회한 뒤 별도 작업으로 세션을 생성하는 방식은 동시 요청에서 세션 제한을 초과할 수 있으므로 사용하지 않는다.

현재 Backend의 세션 수 확인 및 생성 과정에서 동시성 제어가 완전하게 보장되는지는 별도 검증 대상으로 관리한다.

### 9.5 세션 유효기간

세션 만료 정책은 Access Token 및 Refresh Token의 유효기간과 연계하여 정의한다.

다음 항목을 별도로 관리한다.

- Access Token 만료 시간
- Refresh Token 만료 시간
- 세션 유휴 만료 시간
- 최대 세션 유지 시간
- 사용자 로그아웃 시점
- 관리자에 의한 세션 강제 종료 시점

현재 BFF 세션의 만료 시각은 Backend Refresh Token의 JWT `exp` 값을 기준으로 계산한다.

RedisSessionStore는 해당 만료 시각을 기준으로 TTL을 설정한다.

구체적인 유휴 만료 시간 및 최대 세션 유지 시간은 PMIS 운영 정책 확정 후 설정한다.

### 9.6 BFF 세션 저장소

BFF는 `SessionStore` 인터페이스를 통해 세션 저장소 구현을 분리한다.

현재 구현된 저장소는 다음과 같다.

| 구분 | MemorySessionStore | RedisSessionStore |
|---|---|---|
| 저장 위치 | BFF 프로세스 메모리 | Redis 서버 |
| Redis 서버 | 불필요 | 필요 |
| 세션 만료 | 만료 시각 확인 | Redis TTL 및 만료 시각 확인 |
| BFF 재시작 | 세션 소멸 | Redis 데이터 유지 시 세션 유지 |
| 다중 인스턴스 | 세션 공유 불가 | 동일 Redis 사용 시 공유 가능 |
| 사용 환경 | 개발 PC | Redis 사용 환경 및 운영 환경 |

운영 환경에서는 RedisSessionStore를 사용한다.

Redis 키 Prefix는 다음과 같다.

```text
pmis:bff:session:
```

Backend에서 사용하는 임시 로그인 정보 저장 영역과 BFF 세션 저장 영역은 구분한다.

Redis 연결 실패 시 MemorySessionStore로 자동 전환하지 않는다.

운영 환경에서는 Redis 세션 저장소 사용을 필수로 한다.

### 9.7 세션 정보 보호

BFF 서버 측 세션 저장소에는 인증 토큰과 사용자 정보가 저장된다.

따라서 다음 사항을 적용한다.

- Redis 접근 권한 제한
- Redis 접속 정보의 비밀 관리
- 세션 키 및 데이터 접근 통제
- 세션 TTL 설정
- 로그에 토큰 원문 기록 금지
- 세션 데이터의 불필요한 장기 보관 금지

Redis 장애 및 세션 데이터 유실에 대한 복구 정책은 운영 환경 구성 시 별도로 정의한다.

## 10. 로그아웃 및 인증 정보 폐기

### 10.1 로그아웃

로그아웃 요청이 발생하면 다음 순서로 처리하는 것을 목표로 한다.

1. BFF가 로그아웃 요청 수신
2. 현재 BFF 세션 식별
3. Backend에 세션 및 인증 정보 폐기 요청
4. Backend 폐기 결과 확인
5. BFF의 세션 및 토큰 정보 폐기
6. 브라우저 인증 쿠키 만료 처리
7. 로그아웃 결과 반환

현재 BFF 로그아웃 API 및 Backend 세션 폐기 API 연계는 후속 구현 대상이다.

### 10.2 세션 폐기 실패 처리

Backend에서 세션 폐기가 실패한 경우 브라우저 쿠키만 삭제하고 로그아웃이 완료되었다고 처리해서는 안 된다.

세션 폐기 결과와 BFF의 로컬 인증 정보 정리 결과를 구분하여 처리한다.

세션 폐기 실패에 대한 재시도 및 오류 기록 정책은 구현 단계에서 확정한다.

Backend 세션 폐기 실패 시 BFF 세션을 어떻게 유지하거나 격리할 것인지도 함께 설계한다.

### 10.3 관리자 세션 종료

관리자가 특정 사용자의 세션을 종료할 수 있는 기능을 제공하는 경우 다음 사항을 검증한다.

- 관리자 권한
- 대상 사용자 식별
- 대상 세션 식별
- 종료 사유
- 종료 처리 결과

관리자에 의한 세션 종료도 일반 로그아웃과 동일하게 실제 인증 상태가 폐기되어야 한다.

현재 관리자 세션 종료 기능의 BFF 연계는 후속 구현 대상으로 관리한다.

## 11. XSS 및 입력값 보안

### 11.1 XSS 방어

React 화면에 출력되는 데이터는 안전하게 처리한다.

다음 원칙을 적용한다.

- 사용자 입력값을 검증한다.
- HTML을 직접 삽입하는 기능을 최소화한다.
- HTML 렌더링이 필요한 경우 별도의 정화 정책을 적용한다.
- 사용자 입력값을 신뢰하지 않는다.
- CSP 등 브라우저 보안 정책을 검토한다.

HttpOnly 쿠키를 적용하더라도 XSS 공격으로부터 인증된 요청이 실행되는 것을 완전히 방지할 수 없으므로 별도의 방어가 필요하다.

### 11.2 입력값 검증

BFF와 Backend 양쪽에서 입력값을 검증한다.

BFF에서는 요청 구조, 자료형, 필수 항목 및 허용 범위를 확인한다.

Backend에서는 업무 규칙과 데이터 정합성을 최종 검증한다.

### 11.3 파일 업로드 보안

파일 업로드 기능 구현 시 다음 항목을 적용한다.

- 허용 확장자 제한
- 실제 파일 형식 검증
- 파일 크기 제한
- 파일명 및 경로 검증
- 저장 위치 접근 통제
- 악성 파일 검사 정책 검토

클라이언트에서 전달한 Content-Type이나 파일 확장자만으로 파일의 안전성을 판단하지 않는다.

## 12. 비밀 정보 관리

### 12.1 비밀 정보 관리 원칙

다음 정보는 소스 코드에 직접 입력하지 않는다.

- JWT 서명 및 검증 키
- Cookie 서명 키
- 세션 저장소 접속 정보
- DB 계정 및 비밀번호
- 외부 서비스 인증 정보
- 암호화 키

### 12.2 환경 변수 관리

개발 환경에서는 `.env`를 사용하여 설정을 분리한다.

`.env`는 Git 관리 대상에서 제외한다.

`.env.example`에는 실제 비밀 정보가 아닌 예시값만 포함한다.

운영 환경에서는 별도의 Secret 관리 체계를 적용하는 것을 원칙으로 한다.

현재 BFF는 다음 환경 변수를 사용한다.

- `NODE_ENV`
- `HOST`
- `PORT`
- `FRONTEND_ORIGIN`
- `BACKEND_API_URL`
- `SESSION_STORE`
- `REDIS_URL`

운영 환경에서는 `SESSION_STORE=redis`를 필수로 적용한다.

### 12.3 키 교체

인증 및 암호화 키는 교체 가능한 구조로 설계한다.

키 교체 시 기존 세션과 토큰에 미치는 영향을 검토하고 서비스 중단을 최소화할 수 있는 절차를 정의한다.

## 13. 로깅 및 감사

### 13.1 보안 이벤트 기록

다음과 같은 보안 이벤트를 기록한다.

- 로그인 성공 및 실패
- 로그아웃
- 세션 생성
- 세션 종료
- 최대 세션 수 초과
- 권한 없는 API 접근
- CSRF 검증 실패
- Origin 검증 실패
- 인증 토큰 검증 실패
- 관리자에 의한 세션 종료

현재 Fastify 기본 로거는 활성화되어 있다.

다만 위 보안 이벤트를 구조화하여 감사 기록으로 관리하는 기능은 후속 구현 대상이다.

### 13.2 로그 기록 항목

보안 이벤트 로그에는 다음 항목을 포함하는 것을 검토한다.

| 항목 | 설명 |
|---|---|
| 발생 일시 | 이벤트 발생 시간 |
| 이벤트 유형 | 로그인, 로그아웃, 세션 종료 등 |
| 사용자 식별자 | 대상 사용자 |
| 세션 식별자 | 관련 세션 |
| 요청 경로 | 요청 API |
| 결과 | 성공 또는 실패 |
| 실패 사유 | 오류 원인 |
| IP 주소 | 요청 출발지 |
| 추적 ID | 요청 추적용 식별자 |

### 13.3 민감 정보 기록 금지

다음 정보는 로그에 기록하지 않는다.

- 비밀번호
- Access Token 원문
- Refresh Token 원문
- Cookie 원문
- 인증 및 암호화 비밀 키
- 개인정보의 불필요한 상세 내용

로그에 인증 정보가 포함될 수 있는 경우 마스킹 또는 제거 처리를 적용한다.

### 13.4 감사 기록 보호

보안 및 인증 관련 감사 기록은 일반 업무 로그와 구분하여 관리하는 방안을 검토한다.

감사 기록에 대한 조회 권한과 보관 기간은 운영 정책에 따라 정의한다.

## 14. API 오류 처리 보안

인증 및 보안 오류 발생 시 내부 시스템의 상세 정보가 브라우저에 노출되지 않도록 한다.

다음 정보를 외부 응답에 포함하지 않는다.

- 내부 서버 주소
- DB 접속 정보
- 파일 시스템 경로
- Stack Trace
- JWT 검증 키 및 내부 설정
- 상세한 시스템 예외 메시지

브라우저에는 일관된 오류 응답을 제공하고, 상세 원인은 서버 로그에서 확인할 수 있도록 한다.

로그인 실패 응답은 계정 존재 여부나 비밀번호 오류 여부를 과도하게 노출하지 않도록 설계한다.

## 15. 운영 환경 보안 기준

운영 환경에서는 다음 보안 항목을 적용한다.

| 구분 | 보안 기준 |
|---|---|
| 통신 | HTTPS 적용 |
| 인증 쿠키 | HttpOnly 및 Secure 적용 |
| Origin | 허용된 Origin만 허용 |
| CSRF | CSRF 방어 적용 |
| API | Allowlist 기반 Backend 호출 |
| Backend | BFF 및 허용된 내부 시스템만 접근 |
| Database | Backend에서만 접근 |
| Redis | 접근 통제 및 인증 적용 |
| 비밀 정보 | Secret 관리 체계 적용 |
| 로그 | 민감 정보 마스킹 |
| 권한 | 최소 권한 원칙 적용 |
| 세션 | 사용자별 최대 세션 수 및 만료 정책 적용 |
| 오류 | 내부 시스템 정보 비노출 |

추가로 다음 항목을 운영 환경 구성 시 검토한다.

- Reverse Proxy 신뢰 설정
- Rate Limiting 및 로그인 시도 제한
- 보안 이벤트 모니터링
- 취약점 점검 및 패키지 업데이트
- 서버 접근 통제
- 백업 및 복구 정책
- 세션 저장소 가용성 및 장애 대응

## 16. 현재 구현 상태

현재 BFF에서 구현된 보안 관련 구성은 다음과 같다.

| 항목 | 현재 상태 | 비고 |
|---|---|---|
| Fastify 서버 | 구현 완료 | 기본 서버 실행 |
| Helmet | 등록 완료 | 기본 보안 헤더 |
| CORS | 등록 완료 | 환경 변수 기반 Origin 및 Credential 설정 |
| 환경 변수 검증 | 구현 완료 | 필수값, PORT, URL, 세션 저장소 설정 검증 |
| Cookie Plugin | 등록 완료 | `@fastify/cookie` |
| 인증 쿠키 | 구현 완료 | `pmis_session`, HttpOnly |
| Cookie Secure | 구현 완료 | production 환경에서 활성화 |
| Cookie SameSite | 구현 완료 | lax |
| Cookie Path | 구현 완료 | `/` |
| BFF 세션 구조 | 구현 완료 | SessionStore 인터페이스 |
| MemorySessionStore | 구현 완료 | 개발 환경용 |
| RedisSessionStore | 구현 완료 | Redis 기반 세션 저장 |
| Redis TTL | 구현 완료 | Refresh Token 만료 시각 기준 |
| Backend 로그인 연계 | 구현 완료 | 로그인 API 호출 |
| Backend 세션 선택 로그인 연계 | 구현 완료 | 세션 선택 로그인 API 호출 |
| Access Token 저장 | 구현 완료 | BFF 서버 측 세션 저장 |
| Refresh Token 저장 | 구현 완료 | BFF 서버 측 세션 저장 |
| BFF 인증 세션 조회 API | 후속 구현 | `/me` |
| BFF Refresh API | 후속 구현 | Token 갱신 및 회전 처리 |
| BFF Logout API | 후속 구현 | Backend 세션 폐기 연계 |
| 인증 미들웨어 | 후속 구현 | 쿠키 기반 세션 검증 |
| CSRF 방어 | 미구현 | Origin 및 Token 검증 필요 |
| API Allowlist | 미구현 | 일반 업무 API 연계 시 적용 |
| 일반 업무 API 프록시 | 미구현 | BFF를 통한 업무 API 호출 |
| Rate Limiting | 미구현 | 운영 보안 정책에 따라 적용 |
| 보안 감사 로그 | 미구현 | 인증·세션 기능 구현 시 적용 |
| 관리자 세션 강제 종료 연계 | 후속 구현 | Backend 폐기 기능 연계 |
| 동시 로그인 원자성 검증 | 검증 필요 | 세션 제한 동시성 검증 |

현재 구현된 Helmet 및 CORS 설정은 기본 보안 구성이다.

인증 쿠키 발급과 서버 측 세션 저장이 완료되었다고 해서 Cookie 기반 인증 검증, CSRF 및 전체 API 접근 통제가 완료된 상태를 의미하지 않는다.

## 17. 향후 보안 구현 순서

보안 기능은 다음 순서로 설계 및 구현한다.

1. 기존 Spring Boot 인증 구조 및 JWT 발급·검증 방식 확인
2. BFF와 Backend 간 인증 정보 전달 방식 확정
3. JWT 검증 키 및 비밀 정보 관리 방식 확정
4. 인증 쿠키 정책 확정 및 운영 환경 검증
5. 서버 측 세션 조회 및 인증 미들웨어 구현
6. 사용자별 최대 동시 세션 수 관리 검증
7. 로그인·로그아웃·토큰 갱신 API 구현
8. Refresh Token 회전 및 동시 갱신 제어 구현
9. CSRF 및 Origin 검증 구현
10. Backend API Allowlist 적용
11. 보안 이벤트 및 감사 로그 구현
12. Rate Limiting 및 로그인 시도 제한 적용
13. 통합 보안 테스트 수행

각 기능은 Backend 기존 인증 계약과 충돌하지 않도록 확인한 후 구현한다.

## 18. 보안 검증 항목

기능 구현 이후 다음 항목을 검증한다.

| 번호 | 검증 항목 | 기대 결과 |
|---|---|---|
| 1 | 인증 쿠키 HttpOnly 확인 | JavaScript에서 쿠키 직접 접근 불가 |
| 2 | 운영 환경 Secure 확인 | HTTPS에서만 쿠키 전송 |
| 3 | SameSite 설정 확인 | 정의된 정책에 따라 쿠키 전송 제한 |
| 4 | 허용되지 않은 Origin 요청 | 요청 거부 |
| 5 | CSRF Token 누락 요청 | 보호 대상 요청 거부 |
| 6 | 만료된 Access Token | 인증 실패 |
| 7 | 유효하지 않은 Refresh Token | 갱신 실패 |
| 8 | 로그아웃 후 세션 접근 | 인증 실패 |
| 9 | 종료된 세션 재사용 | 인증 실패 |
| 10 | 최대 세션 수 초과 | 사용자 선택 절차 진행 |
| 11 | 동시 로그인 요청 | 최대 세션 수 초과 방지 |
| 12 | Refresh Token 동시 갱신 | 동일 세션의 중복 갱신 충돌 방지 |
| 13 | 임의 Backend URL 호출 | 요청 거부 |
| 14 | 권한 없는 업무 API 호출 | 접근 거부 |
| 15 | 민감 정보 로그 출력 | 토큰 및 비밀번호 미노출 |
| 16 | 비정상 입력값 요청 | 유효성 검증 실패 |
| 17 | Redis 연결 실패 | Memory 저장소로 자동 전환하지 않고 초기화 실패 |
| 18 | Redis 세션 만료 | 만료된 세션 조회 불가 |
| 19 | BFF 재시작 후 Redis 세션 조회 | Redis 데이터가 유지된 경우 세션 조회 가능 |
| 20 | Backend 세션 폐기 실패 | 로그아웃 실패 및 후속 처리 정책 적용 |
